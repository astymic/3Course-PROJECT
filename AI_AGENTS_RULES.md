# Правила для ШІ-Агентів (AI Agents Rules)
## Проєкт: Shoe Factory E-Commerce — Фабрика «LiLu»

Цей файл містить настанови для будь-яких ШІ-асистентів, які допомагають команді у розробці або веденні проєктної документації.

---

## 1. Контекст проєкту
- **Клієнт:** Наталія Кобринська, власниця взуттєвої фабрики «LiLu» (сімейний бізнес).
- **Проблема клієнта:** ручні продажі через Instagram, менеджер фізично ходить на склад перевіряти наявність, замовлення губляться.
- **Мета:** MVP інтернет-магазину з каталогом, обліком складу, кошиком, оплатою, доставкою, popup-консультацією та адмін-панеллю.
- **Конструктор взуття — Фаза 2, НЕ входить у MVP.** Але архітектура має передбачати його.
- **Методологія:** Adaptive / Scrum — 3 спринти по 2 тижні.
- **Термін:** 2 місяці (8 тижнів).
- **Географія:** тільки Україна.

## 3. Мовні та стильові настанови
1. **Мова:** Усі відповіді, тексти, артефакти — **українською мовою**. Виняток: загальноприйняті PM/IT-терміни англійською (*User Story, WBS, Backlog, Sprint, Gantt, Scope, MVP*).
2. **Тон:** Професійний, діловий, орієнтований на PMI/Scrum стандарти.
3. **Структура:** Markdown — параграфи, списки, таблиці. Уникати стін тексту.
4. **Адаптація до ролі:** ШІ повинен розуміти, до якої ролі належить завдання. Якщо питання від PM — фокус на контроль термінів. Від BA — на бізнес-правила та scope. Від Dev/QA — на технічну якість.

## 4. Робота з артефактами
- **Генерація шаблонів:** Якщо потрібно створити документ (Risk Register, WBS, User Stories), ШІ надає Markdown-таблицю з відповідними стовпцями.
- **Специфіка магазину взуття:** При формуванні вимог та User Stories враховувати: розмірну сітку, наявність по розмірах, фото з усіх боків, систему повернення, різні категорії (літнє/зимове), варіації матеріалів (шкіра, нубук, шкірозамінник).
- **MVP vs Фаза 2:** Ніколи не включати конструктор взуття або мобільний додаток у поточний scope.

## 5. Технічні обмеження
- Коментарі в коді — українською.
- Рішення мають відповідати масштабу: 3 людини, 2 місяці, обмежений бюджет.
- Інструменти зафіксовані: Jira для трекінгу, GitHub для коду, обраний інструмент для прототипів.

## 6. Ієрархія документів
1. **TASK.md** — головний документ проєкту. Усі артефакти не мають йому суперечити.
2. **Project Charter** — затверджений з клієнтом scope.
3. **Stakeholders Matrix** — реєстр зацікавлених сторін.
4. У разі конфліктів — пріоритет у TASK.md та Project Charter.
